code style
==========

this is the style guide for everything that ends up in the tree: the kernel
at the root of it, the bootloader under ``boot``, the host suites under
``tests``, the tools under ``tools``, and the assembler sources beside them.
it is written to be enforced, not admired. it follows the conventions C
kernels have long shared, and deviates from them in the places this project
has its own answer: the variable prefixes, the lower-case prose, and
four-space indents instead of eight-wide tabs. those deviations are listed
as deviations, so nobody has to guess which is which.

if you read one paragraph, read this one: **match the file you are
touching.** a diff should look as if it had always been there. a change
that fixes a bug and reformats the surrounding function in the same commit
is two changes wearing one hat, and the second one is the one a reviewer
has to argue with.

scope
-----

applies to:

- C sources and headers, everywhere in the tree: the kernel's directories,
  ``boot/``, ``tests/`` and ``tools/``
- assembler sources. ``*.asm``
- build files. ``GNUmakefile``, ``*.ld``, ``*.mk``
- the python in ``tools/``, against the shorter rules in `python`_

does not apply to:

- vendored or third-party code, wherever it lives
- the console font array, which is generated by ``tools/font2c.py``

language and toolchain
----------------------

C, and only C
   the kernel is C11 (``-std=gnu11``) and freestanding. no hosted libc, no
   ``<stdio.h>``, no ``main``. the programs that run on it are velvetOS's,
   and link against velvetOS's own libc, which is the same C but has fewer
   excuses. there is no C++ in this project and adding one is a discussion,
   not a commit.

fixed-width types by default
   ``uint32_t``, ``uint64_t``, ``size_t``, not ``unsigned long``. the
   machine is 64-bit today and this is what keeps that a fact rather than an
   assumption. ``int`` is fine for a loop index that will never be large;
   anything that indexes memory or counts bytes is ``size_t``.

no floating point in the kernel
   the kernel is built ``-mno-sse -mno-mmx -mno-80387`` because there is no
   fpu context save yet. reaching for a ``float`` there will not link, and
   that is deliberate.

no variable-length arrays
   ``-Wall -Wextra`` is on for every file and a VLA is a stack overflow with
   a compiler's blessing. use a fixed bound and check it.

pointers are not integers
   cast through ``uintptr_t`` when you genuinely have to, and say why in a
   comment on the line.

files and layout
----------------

one translation unit, one header
   every ``foo.c`` that has anything to export has a ``foo.h`` next to it.
   the header is the unit's public interface; everything else in the ``.c``
   is ``static``.

the tree mirrors itself by subsystem
   ``<subsystem>/`` at the root groups by what the code is *for*. ``mm``,
   ``sched``, ``fs``, ``net``, ``drivers``, ``lib``, ``shell``, ``arch``.
   a new subsystem gets a directory, not a file at the root, and its name
   goes in ``sources.mk``, which is the one list of what the kernel is.

include guards
   ``SUBSYSTEM_FILE_H`` in upper snake case, e.g. ``SCHED_PROCESS_H``. no
   ``#pragma once``.

includes
   standard headers first, then project headers, each block alphabetical.
   project headers are quoted and rooted at the include path. ``#include
   "mm/pmm.h"``, never ``"../mm/pmm.h"``.

file headers
   every C source and header opens with the license tag on the first line,
   then a block naming the file, its author as ``NAME <email>, YYYY``, and
   what it is for in at most three lines. the author is whoever wrote the
   file, not the owner of the project.

   .. code-block:: c

      // SPDX-License-Identifier: GPL-2.0-only
      /*
       * sched/sched.c
       * Jose A. Perez de Azpillaga <azpijr@gmail.com>, 2026
       * the scheduler: the run queue, the switch, and reaping the dead.
       */

   the first line is the SPDX identifier, not a pasted copy of the license:
   the root ``LICENSE`` is the license, and the tag is what a tool reads. the
   year is the year the file was written: the year of its first commit, or the
   current year for a new file.

   the header is the whole introduction. there is no second, longer comment
   under it: the subsystem page under ``docs/subsystems/`` is where a file's
   design is explained, and a reader in the file itself needs the brief. a
   leading comment that carries a copyright or licence notice is the one
   exception, and stays exactly where it is.

formatting
----------

indentation
   four spaces. no tabs, anywhere, including the makefile's recipes are the
   one exception because ``make`` requires them. this is a deliberate
   deviation from the kernel's eight-wide tabs: the tree was four before the
   guide, and the smaller indent is what every editor here is set to.

braces
   K&R: the opening brace stays on the line that opens a block, the closing
   brace gets its own line at the parent's indent. the one exception is a
   function *definition*, whose opening brace goes on the line after the
   signature, at the signature's own indent; a function's brace is the one
   the kernel has always put on its own line. a body of one line takes no
   braces; a body of more than one line always takes them, and so does any
   branch of an ``if``/``else`` where one branch needs them.

::

    static bool buffer_has_room(const struct ring *ring, size_t want)
    {
        if (want == 0)
            return true;
        return ring->tail - ring->head + want <= ring->cap;
    }

    static void reset(struct ring *ring)
    {
        if (ring->head != ring->tail) {
            ring->head = ring->tail;
            ring->used = 0;
        }
    }

spaces
   a space after a keyword that takes a condition or a count: ``if``,
   ``for``, ``while``, ``switch``, ``case``, ``do``, ``return``. none after
   ``sizeof``, ``typeof``, ``alignof`` or ``__attribute__``, which look like
   calls. none inside parentheses: ``sizeof(struct file)``, never
   ``sizeof( struct file )``. one space around every binary and ternary
   operator; none after a unary operator (``&``, ``*``, ``+``, ``-``, ``~``,
   ``!``), none around ``++``/``--``, and none around ``.`` or ``->``. a
   pointer binds to the name: ``char *str_name``, ``char **pp_node``, never
   ``char* str_name``. no trailing whitespace on any line.

line length
   eighty columns is the soft cap for code; wrap at roughly seventy-two in
   comments and in the commit body. a long line that is a single
   un-splittable string literal is fine. split the arguments around it,
   not the literal. never break a user-visible string to fit the column: a
   message that cannot be grepped is worse than a long line.

one statement per line
   no ``a = b = c;``, no comma operators outside a ``for`` header, no
   assignment buried inside a condition unless it is the idiom the file
   already uses (``while ((n = read(...)) > 0)``).

naming
------

the type of a variable should be legible at the call site without jumping to
its declaration. that is what the prefix buys, and it is the reason this
project uses prefixes where it could have used nothing. this is a deliberate
deviation from the kernel, which frowns on encoding the type in the name:
here the prefix is short, systematic, and carries scope as well as type, so
it reads as a label rather than as notation.

variable prefixes by type
~~~~~~~~~~~~~~~~~~~~~~~~~

================== ========= ======================
type               prefix    example
================== ========= ======================
bool               ``b_``    ``b_is_ready``
int / int32_t      ``i_``    ``i_frame_count``
unsigned / uint    ``u_``    ``u_ref_count``
size_t             ``sz_``   ``sz_buffer_len``
float              ``f_``    ``f_delta_time``
double             ``d_``    ``d_accum_time``
char               ``c_``    ``c_delimiter``
string / char *    ``str_``  ``str_name``
raw pointer        ``p_``    ``p_buffer``
double pointer     ``pp_``   ``pp_node``
smart pointer      ``sp_``   ``sp_resource``
array / container  ``arr_``  ``arr_vertices``
enum value         ``e_``    ``e_state``
struct instance    *(none)*  ``transform``, ``mesh``
================== ========= ======================

scope-modifying prefixes stack on top of the type prefix:

=============  ========  ===================
scope          prefix    example
=============  ========  ===================
global         ``g_``    ``g_i_frame_count``
static         ``s_``    ``s_p_instance``
member         ``m_``    ``m_f_speed``
=============  ========  ===================

so a static member that is a size_t is ``m_sz_len``; a global raw pointer is
``g_p_table``.

types, functions, constants
~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **types** (``struct`` / ``class`` / ``enum`` names) are ``PascalCase``:
  ``FrameBuffer``, ``SpinLock``, ``FdKind``.
- **functions** are ``snake_case``: ``alloc_buffer()``, ``update_transform()``.
  a function is named for what it does to its receiver, and a public one
  carries its subsystem where that is not obvious from the header it lives
  in.
- **macros and compile-time ``constexpr``/``const`` constants** are
  ``UPPER_SNAKE_CASE``: ``MAX_ENTITIES``, ``PAGE_SIZE``. this is the one
  place an identifier is not lower case, and it is on purpose; it keeps a
  macro visually distinct from a real symbol, which matters the moment one
  is hiding a trap.
- **enum values** are prefixed ``e_`` as instances but the enumerators
  themselves are ``UPPER_SNAKE_CASE`` like constants: ``E_STATE_RUNNING``.

gaps this table does not cover get added to it, not improvised beside it. a
type this project uses often. a ``glm::vec3``, a fixed-point type. gets a
row of its own in the table above before it appears in code.

persona names
~~~~~~~~~~~~~

this project names its pieces after the Persona series: the velvet room,
igor, margaret, theodore, lavenza, the arcana, pixie, and the rest. a new
subsystem, program or feature that wants a name takes one from that series,
one that is not already spoken for and that fits what the thing does.

it is not compulsory. something with no character of its own is fine under a
plain descriptive name. this is a pre-1.0 flavour, and it is expected to fade
once the project reaches 1.0.0.

functions
---------

short, and one thing. a function that no longer fits on a screenful is a
function to split, and a helper with a descriptive name costs nothing and can
be inlined by the compiler if it matters. a long ``switch`` that does one
small thing per case is the exception; complexity is what the limit is
about, not line count.

keep the locals under about ten. a human tracks seven things, and a function
that needs more is usually two functions that have not been separated yet.
separate definitions with one blank line. a prototype carries parameter
names: they document a call, and the compiler does not mind.

comments
--------

comments are for the reader who already knows what the code says and needs
to know *why* it says it.

where an explanation is about the *interface* rather than the implementation
it belongs in ``docs/``. a header is read by people compiling against it, and
what they need from it is the signature. what a function promises, what a
syscall takes and returns, what a field means to a caller, is api
documentation, and it is written once, in the document for that subsystem. the
comment in the code says why the code is shaped the way it is, which is the
one thing the document cannot say, and it is the only reason to keep one.

the test, in two halves. if removing a comment would make one function look
*wrong*, it stays where it is. if removing it would make a subsystem look
*arbitrary*, it belongs in that subsystem's document, and the source keeps a
pointer rather than the essay::

    /* see docs/subsystems/fs.rst, the block layout, for why this copies */

a pointer is one line and it survives a rewrite of the document; an essay
copied into a header is wrong the moment either side changes.

this applies to the main subsystems, which have a document each. a driver
does not: one page per driver would be a worse place to explain a driver
than the driver is, so a driver keeps its explanation where the code is, and
``docs/subsystems/drivers.rst`` describes the shape the drivers share rather
than each one in turn.

- **brief, not a textbook.** a comment explains the one thing the code cannot
  say itself, in a sentence or three. a comment that runs on for a screen is a
  document, and documents live under ``docs/``: the subsystem page is the long
  form, and the file carries its brief.
- **no dashes.** a dash is punctuation this project does not use, in prose or
  in code. write with commas, semicolons, periods and parentheses instead.
  that is no ``--``, no em dash and no en dash.
- **write only for non-obvious logic.** a tricky bit trick, a lock-free
  assumption, an ABI or hardware quirk, a workaround for a bug somewhere
  else, a decision that looks wrong until you know what it prevents. the
  comment explains the decision, not the mechanic. prefer to say it at the
  head of the function rather than in its middle.
- **do not restate the code.** ``/* increment i */ i++;`` is deleted, not
  edited. if the code needs a comment to say what it does, the code is
  wrong, not the comment.
- **comment the data.** one declaration per line, with room for the small
  comment that says what the field is for. a struct is where a reader spends
  the most time and a comment on each field is the cheapest documentation in
  the file.
- **``/* ... */`` always, never ``//``.** a comment that runs over more than
  one line is the kernel's preferred shape: ``/*`` alone on its first line,
  a column of ``*`` on the left, ``*/`` alone on its last.

  .. code-block:: c

     /*
      * This is the preferred style for multi-line
      * comments in the velvet source code.
      * Please use it consistently.
      *
      * Description:  A column of asterisks on the left side,
      * with beginning and ending almost-blank lines.
      */

  a one-line comment stays on its line: ``/* like this */``. a comment that
  trails code may stay where the code ends, but a multi-line one there is
  given the same column rather than left hanging off the statement.
- **doc comments on the public API only.** a function that a caller in
  another unit can see gets a Doxygen block:

  .. code-block:: c

     /**
      * @brief map one page of a user address space.
      * @param p_space the address space to map into.
      * @param virt    the virtual address, page aligned.
      * @param phys    the frame to map there.
      * @param flags   PTE permission bits.
      * @return 0 on success, -ENOMEM if a table could not be allocated.
      */

  internal and ``static`` functions do not get one. they are read with the
  code beside them. do not write a doc block that repeats the signature.
- **lower case prose**, like the rest of the project's writing. proper nouns
  keep their capitals.
- **the code speaks, not an author.** the tree belongs to a community, so a
  comment or a message is written for the project: "the kernel keeps the
  list sorted", not "I keep the list sorted"; "its own page", not "my own
  page"; "the program asks", not "I ask". where the sentence can be an
  instruction, use the imperative: "keep the free list sorted". the Persona
  flourishes are the one exception, and a line that says "thou art I" is
  doing something deliberate.

error handling
--------------

C, so there are no exceptions and no RAII. the shape that has held up:

- **return codes for the kernel.** a function that can fail returns ``0`` on
  success and a negative ``errno``-style value otherwise; a predicate returns
  ``bool``. ``-EINVAL`` for a caller's mistake, ``-ENOMEM`` for the
  allocator, ``-ENOENT`` for a missing name. do not invent a second
  vocabulary.
- **the name decides the convention**, as it does in the kernel. a function
  named as a command returns an error code; a function named as a predicate
  returns a boolean that is true on success: ``add_work()`` returns ``0`` or
  ``-EBUSY``, ``device_present()`` returns ``true`` or ``false``. a function
  whose return value *is* the answer, a pointer or a count, is not subject
  to this and reports failure out of band: ``NULL``, or a value out of
  range.
- **``goto`` cleanup** for a function with more than one exit and more than
  one thing to undo: allocate in order, and have a ladder of labels that each
  undo one step, named for what they do (``out_free_buffer``, not ``err2``).
  this is the one place a ``goto`` is the right answer and the kernel makes
  heavy use of it.
- **``panic()`` is not control flow.** it is for an invariant that has
  already been broken and cannot be repaired. a corrupt boot handoff, a
  page table that will not resolve, an allocator's own books not balancing at
  boot. a ``panic()`` in a path that a running program can reach is a bug in
  the ``panic()``, not in the program.
- **check the pointer ring 3 handed you.** every syscall argument that is a
  user address is validated before it is dereferenced, in one place, in the
  syscall layer. no kernel function trusts a pointer it did not create.

do not crash the machine
------------------------

whether the machine stops is the user's decision, not the code's. an error a
caller can be told about is returned, not asserted on.

- **``panic()`` only at boot**, or for a corruption there is no way to
  continue past.
- **``WARN_ON_ONCE()`` rather than ``WARN``/``WARN_ON``.** a condition that
  can happen twice will happen a thousand times, and a log that wraps is its
  own problem. warn once, and only for something that should never happen at
  all: not a precondition, not ordinary input, not something a program can
  trigger by asking.
- **a compile-time invariant is a static assert**, not a run-time check.
  ``_Static_assert`` is free and speaks during the build, which is the only
  place it needs to.

bool
----

use it. ``true`` and ``false``, never ``1`` and ``0``, and no ``!!`` dance:
converting to ``bool`` already means "is it non-zero", and the double
negation is a class of bug the type was meant to delete. a ``bool`` return
type and a ``bool`` local are always fine.

do not put a ``bool`` in a struct whose layout matters; its size and
alignment are the compiler's business, not yours. if a struct holds many
flags, a bitfield or a single ``uint32_t`` of bits is the honest shape, and
it is also the one that can be handed to a hardware register.

macros and enums
----------------

- **names are ``UPPER_SNAKE_CASE``**, and a macro that behaves like a
  function may be lower case instead.
- **prefer an ``enum``** to a run of related ``#define``s, and a ``static
  inline`` function to a function-like macro.
- **a macro of more than one statement is wrapped** in ``do { ... } while
  (0)`` so that it remains a single statement in an ``if`` without braces.
- **parenthesise the body and every parameter**: ``#define MAX(a, b) ((a) >
  (b) ? (a) : (b))``. an unparenthesised argument is a precedence bug with a
  delay fuse.
- **a macro must not leave its caller.** no ``return``, no ``break``, no
  ``goto`` out of a macro, however convenient it looks where it is written.
- **a function-like macro must not need a local of a particular name**, and
  must not name one that can collide; prefix anything it declares.

typedefs
--------

do not hide a struct or a pointer behind one. ``struct foo *p_bar`` says what
it is at the call site; ``foo_t p_bar`` does not, and the reader has to go
find out. there are two cases worth a typedef, and neither is "it is shorter":

- a genuinely opaque type with accessors, where the point is that the shape
  is not the caller's business.
- the fixed-width integer spellings this project already uses.

new types that are only a shorter spelling of a standard one are not a
reason.

allocation
----------

the size handed to an allocator is the size of the thing written into it:
``kmalloc(sizeof *p_x)``, not a second, separately maintained spelling of
the type, which goes stale the moment the pointer's type changes. do not
cast the ``void *`` that comes back; C converts it, and the cast only hides
the warning you were meant to see. an allocation failure is an ordinary
error return, not a ``panic()``, unless it is boot and there is genuinely
nothing else to do.

inline
------

``inline`` is not a speed switch. it is worth reaching for a small function
the compiler cannot see across, or one whose parameter must be a compile-time
constant so the body optimises away. a function of more than a few lines, or
one that is already written once, is not that, and the icache it costs is
paid by everything else. mark it ``static`` and let the compiler decide
unless you have a reason.

conditional compilation
-----------------------

wherever a ``#if`` will do, a header with a real function and a no-op stub
in the ``#else`` will do better: the compiler then checks both sides, and
the logic stays in C where it can be read. compile whole functions out
rather than fragments of them, and factor an expression out of an ``#if``
into a small function rather than guarding the expression in place. a
non-trivial ``#endif`` is followed by a comment naming what it closed::

    #ifdef CONFIG_SOMETHING
    ...
    #endif /* CONFIG_SOMETHING */

the arch boundary
-----------------

this is the rule the build actually enforces, and the one most worth
internalising before touching anything under ``kernel``:

**machine-specific code lives under ``arch/<machine>/`` and nowhere else.**

everything above that line is supposed to be portable. ``arch/x86_64/``
holds the port i/o, the gdt/idt, the isr stubs, the pic and io apic, the
tss, the msr constants and the context switch. a file outside ``arch/``
that needs an x86 header, a line of inline assembly, or a register it names
by hand is a file with a leak in it.

the boundary is not a convention, it is a check. ``tools/checkarch.py``
greps for inline asm and x86 includes outside ``arch/`` and fails the build;
``tools/portable.py`` compiles the portable half against
``arch/none/``. an architecture whose every function returns a deliberate
lie, and fails on anything that cannot build against a machine that does
not exist. ``make portable-check`` is part of ``make test`` and therefore
part of CI. see `building`_ and `the architecture boundary
<subsystems/arch.rst>`_ for what the headers are.

the headers under ``arch/`` are named for what the *rest of the kernel
wants*, not for what x86 provides: ``irq.h`` (may interrupts happen),
``cpu.h`` (what this core is), ``mmu.h`` (what the hardware must be told
about a page table), ``machine.h`` (the box: reset, power, a key). keep it
that way. ``write_cr3()`` behind a portable-looking name is worse than the
inline asm it replaced, because the inline asm was honest.

testability
-----------

the kernel is testable without booting it because the parts that think do
not reach for the parts that touch hardware. preserve that seam:

- **take the input as an argument.** ``pmm_init_from_map()`` takes a memory
  map rather than asking the loader; ``keyboard_feed()`` takes a scancode
  rather than reading a port; ``serial_feed()`` takes a byte; ``run_line()``
  takes a string. the test then fabricates the input and calls the real
  function.
- **``VELVETOS_HOSTED``** is defined for host builds and turns ``irq_save``
  / ``irq_restore`` into no-ops, because userspace is not allowed to
  ``cli``. a new hardware-touching path that has no host seam should say so
  out loud, in the commit, rather than silently becoming untestable.

markers: TODO, FIXME, XXX, NOTE, HACK
-------------------------------------

these are for things that outlive the commit that introduces them. a marker
with no reason is deleted, not merged. the form is::

    /* FIXME: what is wrong, and why it is wrong. */

``TODO``
    a known gap. nothing is broken; something is not done. say what unlocks
    it. a later version, a missing subsystem, a decision that has not been
    made.

    .. code-block:: c

       /* TODO: use the extent map once ext4 writes them */

``FIXME``
    wrong today, and must be fixed. something behaves incorrectly, or will at
    the first opportunity. say what is broken and what the correct behaviour
    is.

    .. code-block:: c

       /* FIXME: this drops the low byte when remaining < 8 */

``XXX``
    dangerous, or holding a sharp edge. correct as far as it goes, but
    fragile, racy, or one refactor away from a bug. say what the failure mode
    is.

    .. code-block:: c

       /* XXX: relies on the caller holding the table lock */

``HACK``
    deliberate, ugly, and temporary. say what the proper fix is, and why it
    was not done here.

``NOTE``
    non-obvious, and not a defect. context a reader needs and the code cannot
    carry on its own.

rules:

- **no name goes in a marker.** a marker belongs to whoever picks it up. the
  tree is a community's, the person who fixes it is rarely the one who wrote
  it, and a name in a comment is a claim about who owns a problem, which is
  not a thing this project wants to say.
- the reason is not optional. ``TODO:`` with nothing after it is a smell: a
  marker that says nothing the code does not already say is deleted.
- a marker does not excuse a missing test. if the code is wrong, the commit
  that fixes it for real brings the test; the marker is for what cannot be
  fixed yet, and says why.
- do not use a marker where a version is the answer. if `the roadmap
  <../ROADMAP.md>`_ already schedules the work, name the version instead, so
  the marker and the roadmap agree.
- markers are greppable on purpose. keep them on their own line, and keep
  the marker word at the start, so one ``rg`` finds every loose end in the
  tree.

artificial assistance
---------------------

if a model wrote it, helped write it, or suggested it, the commit says so::

    Assisted-by: <tool>

that is the whole rule, and it is required rather than requested. it covers
code, a test, a comment, a commit message, an argument made in review, and an
idea that turned into a change. one trailer, next to the sign off, naming the
tool, because "an llm" is not a useful fact and "gpt-5, then rewritten by
hand" is.

**why it is here.** the sign off says you have the right to send the change;
this trailer says how the change was made, which is the one thing a reviewer
cannot read out of a diff and cannot ask about a year later. a patch with the
trailer is read like any other patch. a patch without one, that reads like a
model wrote it and nobody read it back, is a patch that gets sent back,
because its author cannot answer for it.

**and it is not a ban.** a model that finds a bug, writes a test or drafts a
paragraph is a tool, and refusing tools is not a virtue. what is not
acceptable is a change its author cannot explain: if a line is there because
the model put it there and you did not check, it is not ready, exactly as a
patch copied from somewhere you did not read is not ready. see `the sign-off
line in the contributing guide <contributing.rst>`_ for where the trailer
goes.

tests
-----

calling the code and asserting on the answer is part of writing the code, not
a follow-up. the suite for a subsystem lives in ``tests/test_<subsystem>.c``
and compiles the *real* sources as an ordinary linux program.

- ``CHECK(cond, "what failed")`` counts a failure and keeps going, so one bad
  run reports every bad case rather than the first.
- a panic path in the code under test gets a ``panic()`` stub that exits, so
  the suite fails instead of taking the runner down.
- test the real output where there is one. ``tests/test_inflate.c`` runs
  against zlib's bytes, ``tests/test_epoch.c`` against the host's own
  ``timegm``. a second
  opinion from somebody else's implementation is worth more than a fixture
  this project wrote to agree with itself.

see `testing`_ for how to run them and what CI does with them.

assembler
---------

``.asm`` files are NASM syntax, assembled with ``nasm -f elf64``. the same
four-space indent, the same lower-case prose in comments (``;`` rather than
``/* */``). labels and symbols follow the naming rules above where they are
C-visible: a symbol the linker resolves is lower case snake case, a macro is
upper snake case.

python
------

the tools are ordinary python 3 with no third-party imports. anything in
``tools/`` has to run on a machine that has nothing but a python interpreter
and the project. standard library only, ``#!/usr/bin/env python3``, a
module docstring saying what the tool is for rather than what it does, and
``sys.exit(1)`` on a failed check so ``make`` stops. the naming rules are
relaxed here: python is not the project's implementation language and
pretending otherwise buys nothing. keep the same comment rule. the module
docstring explains *why the tool exists*, which for most of these is "this
checked a bug that cost an afternoon".

conformance and migration
-------------------------

the mechanical half of this guide has been applied to the tree. the file
headers, the multi-line comment shape and the function brace rule are now
uniform across the kernel, ``boot``, ``tests`` and ``tools``. a change like
that lands as its own commit with no behaviour change in it, and the object
files it produces are the ones it produced before, which is how it was
checked.

what is left is not mechanical: the naming rules. the tree predates them;
it has lower-case struct types and no variable prefixes, and that is what the
guide asks to change.

the rules for that gap:

- **new code follows the guide.** a new file, and a new function in an
  existing file, are written to this document. nobody writes a new prefixed
  variable in a file that has none and feels bad about it.
- **existing code is grandfathered, and a file is converted when it is worth
  converting.** conversion happens as its own commit, with no behaviour
  change in it, so the diff is a style diff and nothing else.
- **never mix the two.** a bug fix that also renames every variable in the
  function is two commits, and the reviewer gets to see each one.
- **the machine's half is ``tools/lint.py``.** it reads ``git ls-files`` and
  checks the rules in this document that need no judgement: the file header,
  the shape of a multi-line comment, the function brace, dashes and first
  person in prose, tabs and the ``//`` rule. it runs
  as ``make lint``, or on the files you are touching as
  ``make lint FILES='fs/ext4.c'``. ci runs it before anything is built, so a
  style error is the first thing a pull request hears about.

  naming prefixes come out as warnings rather than errors, because the tree
  predates that rule: a clean run still prints a count, and the count is the
  migration left to do. ``--strict`` makes the warnings fatal, which is what a
  converted file can be held to.
